# 项目成果报告 → 专利交底书转化指南

## 适用场景

用户提供的源材料是"五小专利申报材料""科技成果报告""项目总结""创新成果推荐书"等成果类文档，需要转化为联通专利交底书。

## 成果报告 vs 交底书的本质差异

| 维度 | 成果报告（五小/科技奖） | 专利交底书 |
|------|----------------------|-----------|
| 核心目的 | 证明项目价值、评奖评优 | 限定保护范围、支撑专利审查 |
| 叙事视角 | "我们做了什么、效果如何" | "现有技术有什么问题、本方案如何解决" |
| 创新点写法 | 列举亮点，偏宣传性 | 提炼区别技术特征组合，偏法律性 |
| 效果数据 | 直接展示业绩 | 作为技术效果的证据支撑 |
| 技术深度 | 概括性描述，避免过于细节 | 必须到可实施级别，输入/处理/输出/公式 |
| 检索对比 | 通常不涉及 | 必须有一手来源核验的现有技术对比 |

## 转化步骤

### 1. 从成果报告提取"发明事实表"

成果报告通常包含以下可复用信息：
- **实施背景** → 提炼现有技术缺点（注意：成果报告的背景偏业务痛点，需转化为技术缺点）
- **需要解决的主要问题** → 直接对应技术问题，但需去掉业务语言
- **总体思路与技术路线** → 提取技术架构和方法框架
- **主要创新内容** → 提取技术手段细节（注意：成果报告的创新点可能过于宏观，需拆解为可实施步骤）
- **实施成效/效果** → 作为技术效果的量化证据
- **创新点** → 初步保护点候选（注意：需转化为"技术特征组合"而非"功能亮点"）

### 2. 补充成果报告缺失的内容

成果报告通常缺少以下交底书必需内容：
- **最接近现有技术对比**：成果报告不做检索对比，需另做
- **完整可实施技术方案**：成果报告往往概括描述，需补充输入/处理/输出/中间数据/判定规则/异常分支
- **公式**：成果报告通常不含公式，需根据技术方案判断是否需要
- **替代方案**：成果报告不讨论替代实现，需根据技术手段设计
- **内容对应关系表**：成果报告不要求缺点→问题→手段→效果→保护点的严格对应

### 3. 语言转化规则

| 成果报告语言 | 交底书语言 |
|-------------|-----------|
| "形成贯穿XX的AI运营闭环" | "一种XX方法，包括步骤S1…S2…S3…" |
| "降低学习和准备成本" | "减少一线人员的操作步骤从N步降至M步" |
| "具有较强的实用性" | 删除（专利不使用主观评价） |
| "复用既有数据、系统和触点" | "基于已有的XX数据接口和YY系统调用协议" |
| "轻量化编排" | "通过ZZ协议进行标准化数据接入和任务调度" |
| "入围XX奖" | 删除（与技术方案无关） |
| "小切口重组" | 删除（非技术术语） |

### 4. 保护点提炼原则

成果报告的"创新点"通常是功能层面的亮点列举，需要转化为技术特征组合：

**错误转化**：直接把成果报告创新点搬到交底书
- ❌ "MCP+Skill+Agent协同编排创新"

**正确转化**：提炼为方法步骤+数据结构+技术关系
- ✅ "一种面向运营商一线营销服务的AI运营方法，其特征在于采用MCP上下文接入层、Skill业务技能层和Agent智能体编排层的三层协同架构，其中：MCP层统一接入…形成…；Skill层将…沉淀为…；Agent层根据…自动编排调用…"

### 5. 效果数据的使用

- 成果报告的效果数据可直接引用，但需标注来源（如"根据系统运行数据"）
- 效果数据必须与技术手段有因果关系
- 不要把经济效益（合同金额）当作技术效果
- 转化率、准确率等技术指标才是技术效果的直接证据

## 常见坑

1. **把成果报告的"推广价值"段落当"落地可能性"**：交底书的落地可能性要求已落地的产品/系统/版本，不是"可以推广"
2. **保留成果报告的宣传性语言**：交底书需全部转化为客观技术语言
3. **缺少可实施细节**：成果报告说"采用大模型进行语义理解"，交底书需要写清楚输入是什么、模型做什么处理、输出是什么、怎么进入下一步
4. **忽略异常分支**：成果报告只描述正常流程，交底书需要覆盖数据缺失、模型置信度不足、规则冲突等异常情况
5. **把团队荣誉写进交底书**：竞赛获奖、论文发表只在"是否已发表"部分提及，不写入技术方案
