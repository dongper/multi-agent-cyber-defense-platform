2. 某动态防护产品WAF技术原理

2.1 整体架构

某动态防护产品 WAF 的核心是一个 VM 字节码解释器（$_ts 全局对象），混淆后的 JavaScript 代码通过 VM 动态执行。页面加载时 VM 启动，接管 XMLHttpRequest.prototype，此后所有 XHR 请求被自动加密。

┌─────────────────────────────────────────────────────┐
│                    页面加载流程                       │
├─────────────────────────────────────────────────────┤
│ 1. HTML 返回（含 <script> $_ts 初始化）               │
│ 2. $_ts.cd = "..."  配置/密钥注入                    │
│ 3. VM 字节码解释器加载（241KB+ 混淆 JS）              │
│ 4. VM 启动，接管 XMLHttpRequest.prototype             │
│ 5. 此后所有 XHR/Fetch 请求被自动加密                  │
└─────────────────────────────────────────────────────┘

2.2 请求加密流水线

页面代码调用 XHR 发送原始请求 → 经过某动态防护产品 Hook 处理后变成：

原始请求:
  POST /api/web/login
  Content-Type: application/json
  Body: {"account":"138****8000","password":"[REDACTED]","captcha":"abcd"}

某动态防护产品加密后:
  POST /api/web/login?SIG_PARAM=08JeDvqlqWWxiMr7Al9xcyNgwkAIxNJA...（签名参数）
  Content-Type: application/x-www-form-urlencoded
  Body: [加密后的表单数据，整个 JSON 被重新封装]
  Cookie: WAF_SESSION_[REDACTED]=...（会话令牌）

某动态防护产品做了三件事： 1. URL 注入：添加随机参数名（如 SIG_PARAM），值为 Base64 加密签名 2. Body 重封装：将整个原始 Body 加密，放入随机命名的参数中 3. Cookie 管理：设置 Session Token + Verification Payload

2.3 VM 字节码解释器

某动态防护产品的核心是 $_ts 下的栈式虚拟机。所有字符串（函数名、参数名、URL）通过解密函数动态还原，依赖动态计算的密钥表。这就是为什么 Function.prototype 和 eval 不能被 Hook —— VM 依赖 new Function() 动态编译字节码，拦截会破坏函数表导致 VM 崩溃。

2.4 Cookie 体系

Cookie 长度 作用
WAF_SESSION_[REDACTED] ~101 字符 Session Token，标识已验证会话
WAF_VERIFY_[REDACTED] ~505 字符 Verification Payload，包含浏览器指纹/验证数据

浏览器首次访问时，某动态防护产品注入挑战页面（412 + HTML + JS），浏览器执行验证 JS 后获得 Cookie。之后的请求携带 Cookie 即被认为"已验证"。

2.5 签名参数特征

某动态防护产品在不同站点注入的签名参数名随机变化，但具有统一特征：

特征 示例值 判断依据
参数名长度 SIG_PARAM（6字符） ≥ 5 字符
参数名字符集 Base64 字符 + . _ - /^[A-Za-z0-9+/=._-]{5,}$/
参数值长度 200+ 字符 > 20 字符
参数名随机性 每个请求都可能不同 无固定参数名

3. 绕过原理

3.1 核心思路：原型链逃逸

某动态防护产品 Hook 在原型链上：

XMLHttpRequest.prototype.open   ← 某动态防护产品包装
XMLHttpRequest.prototype.send   ← 某动态防护产品包装（加密在这里发生）

绕过方法：在 @run-at document-start（最早时机，某动态防护产品加载前）保存原生引用，以 .call(xhr, ...) 方式调用，跳过原型链。

// document-start: 某动态防护产品之前保存
const _NativeXHR_proto_send = XMLHttpRequest.prototype.send;  // 此时还是原生的！
const _NativeXHR_proto_open = XMLHttpRequest.prototype.open;

// 之后某动态防护产品加载，修改了 prototype.send / prototype.open
// 但我们的 _NativeXHR_proto_* 引用的是原始函数

// 发送绕过请求:
const xhr = new XMLHttpRequest();
_NativeXHR_proto_open.call(xhr, 'POST', '/api/xxx', true);  // .call 跳过原型链
_NativeXHR_proto_send.call(xhr, originalBody);               // 不经过某动态防护产品加密

技术关键点：document-start 是最早的脚本执行时机，早于页面上任何 <script> 标签。此时 XMLHttpRequest.prototype 还是浏览器原生的，保存引用后再由某动态防护产品篡改，我们的引用不受影响。

3.2 实例级 Hook：捕获原始参数

光绕过不够，还需要监控。但如果在原型链上监控，只会看到加密后的数据。解决方案是实例属性覆盖：

// open() 包装中，给每个 XHR 实例挂自己的 send
XMLHttpRequest.prototype.open = function(method, url, ...) {
    this.__vv = { method, url, headers: {}, startTime: Date.now() };

    if (!this.__vv_hooked) {
        this.__vv_hooked = true;
        const protoSend = this.send;  // 当前原型上的 send

        // ★ 实例属性 send 覆盖原型方法
        this.send = function(body) {
            // ★ 此时 body 还是原始 JSON 或 FormData！
            // 因为实例属性优先于原型属性（JS 属性查找规则）
            xhr.__vv.body = body;
            return protoSend.call(this, body);  // 再走某动态防护产品加密
        };
    }

    return _origOpen.call(this, method, url, ...);
};

调用链可视化：

页面代码 xhr.send(原始JSON)
  │
  ▼
实例方法 this.send  ← 我们的 Hook（★ 捕获原始 body）
  │
  ▼
原型 XMLHttpRequest.prototype.send  ← 某动态防护产品包装（加密 body + 注入签名到 URL）
  │
  ▼
原生 send()  ← 真正发出 HTTP 请求

实例属性在原型链查找中优先级最高（JS 规范），所以我们的 Hook 总在某动态防护产品之前执行。这个机制与站点无关，对所有某动态防护产品版本通用。

3.3 反调试：最小化策略

某动态防护产品 JS 中通常包含 setInterval(function(){debugger}, ...) 循环阻碍调试。

错误做法：Hook Function.prototype.constructor 和 eval → 某动态防护产品 VM 的 new Function() 调用被拦截 → 函数表损坏 → 签名异常 → 412。

正确做法（最小化干预）： 1. console.clear → 静默阻止（保留原生引用供手动清理） 2. setInterval(function(){debugger}, ...) → 精确匹配函数体字符串，返回 -1 阻止 3. 不碰 Function / eval / constructor

// 精确拦截 debugger 定时器
const _origSetInterval = window.setInterval;
window.setInterval = function(fn, delay) {
    const fnStr = String(fn).replace(/\s+/g, '');
    if (fnStr === 'function(){debugger}' || fnStr === 'function(){debugger;}') {
        return -1;  // 返回无效 ID，不执行
    }
    return _origSetInterval.call(this, fn, delay);
};

3.4 为什么从 Yakit/Burp 直发会 412

┌──────────────────────┬──────────────────────────┐
│   浏览器内                  │   Yakit/Burp 外部直发        │
├──────────────────────┼──────────────────────────┤
│ 浏览器 TLS 指纹           │ 工具自身 HTTP 栈指纹         │
│ 浏览器 HTTP/2 特征        │ 不同的 HTTP 栈特征            │
│ 完整的 Cookie 上下文      │ 只有手动粘贴的 Cookie         │
│ $_ts VM 环境存在          │ 无 VM 环境                    │
├──────────────────────┼──────────────────────────┤
│ → WAF: 已验证的会话      │ → WAF: 新客户端，挑战！        │
│ → 200 业务响应 ✅         │ → 412 + Ruishu JS 挑战 ❌     │
└──────────────────────┴──────────────────────────┘

解决方案就是热加载桥接：让 Yakit/Burp 修改的参数回到浏览器中，用已验证的会话发送。

4. 前端应用层加密分析（非重要部分，未实践，可跳过）

4.1 两层加密模型

某动态防护产品 WAF 的加密不是唯一需要关注的。许多 Web 应用在调用 XHR 之前，先对敏感字段（如密码）做了应用层加密。理解这两层的关系至关重要：

用户输入 password = "[REDACTED]"
        │
        ▼
   ┌─────────────────────────────┐
   │ ① 应用层加密（前端 JS）      │  ← 本节重点
   │   AES / RSA / SM2 / SM4     │
   │   → "[REDACTED_CIPHERTEXT]"
   └──────────────┬──────────────┘
                  │
                  ▼
   xhr.send('{"password":"Se9tt/..."}')  ← 油猴脚本在此截获
                  │
                  ▼
   ┌─────────────────────────────┐
   │ ② 某动态防护产品 WAF 加密（传输层）    │  ← 第2-3章已解决
   │   Body 混淆 + URL 签名注入  │
   └──────────────┬──────────────┘
                  │
                  ▼
            发送到服务器

油猴脚本的能力边界：

能力 状态 说明
截获加密前 body（对某动态防护产品而言） ✅ 在某动态防护产品包装之前拿到 body
剥离某动态防护产品签名参数 ✅ 双方案自动识别
桥接转发 ✅ Yakit → bridge → 浏览器 → 服务器
解密应用层加密 ❌ password 的加密发生在 xhr.send 之前，可保存整个网页让投喂给AI反混淆解密获取加密算法。

4.2 应用层加密常见形态

加密库 典型特征 常见场景
CryptoJS CryptoJS.AES.encrypt(...) 传统 webpack 项目
JSEncrypt new JSEncrypt() + setPublicKey() RSA 非对称加密
window.crypto.subtle crypto.subtle.encrypt(...) 现代浏览器原生 API
sm-crypto sm2.doEncrypt(...) / sm4.encrypt(...) 国密算法（政务/金融）
自研混淆 自定义算法 + VM 保护 高安全性需求场景

4.3 加密函数定位方法论

即使代码被混淆/打包（webpack），加密函数仍可通过以下不可混淆的指纹定位：

步骤一：从 XHR Body 倒推

脚本截获的 body 中看到加密字段：

{"password":"[REDACTED_CIPHERTEXT]"}

步骤二：并行搜索四个维度

在保存的站点 JS 文件中，用多个关键词并行搜索：

搜索目标 关键词 目的
body 构造点 password、字段名 找到赋值位置
加密函数名 encrypt、Encrypt、decrypt 直接命中
Base64 工具 base64、btoa、[A-Za-z0-9+/=] 加密输出通常带 Base64
算法实现 0x63,0x7c,0x77（AES S-box）、PKCS7、010001（RSA 公钥指数）、subtle 确认具体算法

步骤三：调用栈回溯

若关键词搜索无果，在脚本中添加 Hook 打印调用栈：

// 在实例级 Hook 中增加：
this.send = function(body) {
    console.group('[VV] 调用栈追踪');
    console.trace('XHR send 被调用');  // ← 从这里往上追溯加密调用
    console.groupEnd();
    xhr.__vv.body = body;
    return protoSend.call(this, body);
};

调用栈会显示从业务代码到 xhr.send 的完整函数调用链，混淆改不了函数调用关系。

步骤四：确认算法

找到加密函数后，看函数内部实现确认算法：

指纹特征 算法判定
"\x01\x00\x01" 或指数 65537 RSA 公钥
S-box 数组 [0x63, 0x7c, 0x77, ...] AES
PKCS7 / Pkcs7 / padding 逻辑 AES/DES 的填充模式
mode: {CBC: ...} 或 iv 参数 对称加密的 CBC 模式
字符串 "AES" / "RSA" 作为字面量 直接调用标准库
SM2 / SM4 / SM3 字面量 国密算法
crypto.subtle.encrypt Web Crypto API

4.6 自动化 Hook 脚本模板

在油猴脚本中添加以下代码，可在任意站点自动嗅探加密行为：

// 加密函数自动嗅探（实验性功能，按需启用）
function _sniffEncryption() {
    // Hook 所有可能被用作加密的全局函数
    const candidates = [];
    for (const key of Object.getOwnPropertyNames(window)) {
        try {
            const val = window[key];
            if (typeof val === 'function' && /^[a-z]/.test(key)) {
                const str = String(val).toLowerCase();
                if (str.includes('encrypt') || str.includes('base64') ||
                    str.includes('aes') || str.includes('rsa') || str.includes('cipher')) {
                    candidates.push(key);
                }
            }
        } catch(e) {}
    }
    console.info('[VV] 🔍 潜在加密函数:', candidates);
    return candidates;
}

// 对所有 XHR body 做全量搜索
function _findEncInBody() {
    const bodies = requestLog.map(e => e.originalBody).filter(Boolean);
    // 正则匹配疑似加密的字段值（Base64 编码特征）
    const encryptedPattern = /[A-Za-z0-9+/=]{32,}/g;
    bodies.forEach(body => {
        const matches = String(body).match(encryptedPattern);
        if (matches) console.info('[VV] 🔐 疑似加密字段:', matches);
    });
}

注：自动嗅探模块不在油猴主脚本中，仅作为可选的扩展。按需添加到具体站点适配脚本中。

5. 安装与部署

5.1 安装油猴脚本

  1. 安装 Tampermonkey 浏览器扩展（Chrome / Edge / Firefox 均支持）

  2. 在 Tampermonkey 管理面板中点击 新建脚本

  3. 将 某动态防护产品WAF分析-油猴脚本.user.js 全部内容粘贴到编辑器中

  4. 确认以下关键配置：

// ==UserScript==
// @name         某动态防护产品WAF Hook分析
// @match        https://security-lab.example.internal/*
// @run-at       document-start          ← ★ 必须，早于某动态防护产品加载
// @grant        none
// @inject-into  page                    ← ★ 必须，注入页面上下文
// ==/UserScript==
  1. 保存（Ctrl+S），确认脚本状态为已启用

⚠️ 关键：@run-at document-start + @inject-into page 两个配置缺一不可。前者确保在某动态防护产品之前保存原生 XHR 引用；后者确保脚本运行在页面上下文（而非 Tampermonkey 沙箱），这样 console.info 和 DOM 操作才能正常工作。

5.2 安装桥接服务器依赖

5.3 配置桥接服务器

6. 控制台命令详解（可直接使用按钮，不重要）

所有命令通过 window.__VV 调用（简写 __VV）。

6.1 监控与分析

__VV.catalog(filter?)

列出所有已捕获的 API 端点及参数。

__VV.catalog()          // 全部端点
__VV.catalog("login")   // 筛选含 "login" 的端点

// 输出示例:
// ✅ POST|GET  /api/web/login
//  调用次数: 3
//  #1 [200] body: {"account":"138****8000","password":"xxx",...}

__VV.inspect(index?)

查看单条请求的完整详情。

__VV.inspect()     // 最新一条
__VV.inspect(3)    // 第 3 条

// 输出:
// 🔍 请求 #3 详情
// 端点: POST /api/web/login
// 完整URL: https://security-lab.example.internal/api/web/login?SIG_PARAM=...
// Headers: {Content-Type: "application/json", ...}
// Body (原始，加密前): {"account":"138...","password":"xxx",...}
// Status: 200
// 💡 重放: __VV.replay(3, { body: '...' })
// 💡 导出: __VV.toYakit(3)

__VV.getLog()

返回完整的请求日志数组 requestLog，可用于程序化分析。

// 筛选所有 POST 请求
__VV.getLog().filter(e => e.method === 'POST')

// 筛选所有 4xx 响应
__VV.getLog().filter(e => e.status >= 400)

__VV.clearLog()

清空所有请求记录、端点目录和控制台。

6.2 绕过与发送

__VV.sendRawRequest(url, options)

核心函数：使用原生 XHR 引用发送请求，完全绕过某动态防护产品加密链。

// POST JSON
__VV.sendRawRequest('/api/web/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
        account: '138****8000',
        password: 'xxxxxx',
        captcha: 'abcd'
    })
}).then(r => console.log(r.status, r.body))

// GET 请求
__VV.sendRawRequest('/api/web/captcha', {
    method: 'GET'
}).then(r => console.log(r.status))
参数 类型 说明
url string 相对路径或完整 URL
options.method string HTTP 方法，默认 GET
options.headers object 请求头键值对
options.body string / null 请求体字符串

返回值：Promise<{status, statusText, headers, body}>

技术细节：使用 document-start 保存的 _NativeXHR 构造函数创建 XHR 实例，再用 _NativeXHR_proto_open.call() 和 _NativeXHR_proto_send.call() 调用原生方法。全程不经过 XMLHttpRequest.prototype 上的某动态防护产品包装函数。自动携带浏览器 Cookie（xhr.withCredentials = true），14 秒超时。

6.3 参数篡改

__VV.replay(identifier, overrides)

基于已捕获的请求模板，修改任意参数后重新发送。

// identifier = 数字索引
__VV.replay(3, { body: JSON.stringify({account: "13900000001", ...}) })

// identifier = 端点路径（自动匹配最新一条）
__VV.replay("/api/web/login", { body: '{"account":"root"}' })

// 修改参数（覆盖 body）
__VV.replay(3, { body: '{"account":"demo_user","password":"[REDACTED]"}' })

// 修改 URL query 参数
__VV.replay("/api/web/sendSms", { params: { mobile: "13900000001" } })

// 修改请求头
__VV.replay(3, { headers: { 'X-Custom': '[REDACTED]' } })

overrides 支持的全部字段：

字段 类型 说明
body string 完全替换 body
params object 覆盖 URL query 参数
headers object 合并/覆盖请求头
method string 覆盖 HTTP 方法
url string 覆盖完整 URL

6.4 导出

__VV.toYakit(index?, options?)

导出为发往桥接服务器的 JSON 请求包，直接粘贴到 Yakit WebFuzzer 即可发送。

// 指定序号导出（默认自动剥离某动态防护产品签名参数）

// 保留签名参数（分析用）

Content-Type: application/json

自动剥离逻辑（_stripRSQuery）：

采用双方案策略：

方案 触发条件 方式 特点
A（优先） _rsParamNames 已探明参数名 精确匹配删除 快、准、不误伤
B（兜底） 尚未探明任何参数名 正则启发式扫描 自动发现 + 同步记录到方案 A

每次 XHR 请求捕获时，_detectRSKeys() 自动学习签名参数名。最终效果：?SIG_PARAM=xxx...&account=138... → ?account=138...（签名参数被剥离）。

8. Yakit 热加载桥接

8.1 为什么需要桥接

在 Yakit 中修改参数后直发会返回 412（Precondition Failed），因为 WAF 检测到请求来自不同的 HTTP 客户端。

桥接的解决方案：Yakit 把修改后的 JSON 请求发给本地 Python 服务器 → WebSocket 转发到浏览器 → 浏览器用已验证会话的原生 XHR 发送 → 响应原路返回。

┌─────────┐  HTTP JSON  ┌──────────────┐  WebSocket   ┌──────────┐  原生XHR   ┌──────────────┐
│  Yakit  │ ──────────→ │ bridge_server │ ───────────→ │ 浏览器    │ ─────────→ │ security-lab   │
│(改参数)  │ ←────────── │   .py :9998   │ ←─────────── │ (油猴脚本) │ ←───────── │   .com:443 │
└─────────┘  响应 JSON   └──────────────┘   响应 JSON   └──────────┘  响应       └──────────────┘

与代理工具（Burp/Yakit MITM）的本质区别：

特性 bridge_server.py 传统 MITM 代理
请求路径 浏览器主动发送 代理转发 TLS 流量
某动态防护产品签名 浏览器 JS 自动生成 无 JS 环境，无法生成
TLS 认证 浏览器原生 TLS 代理需安装 CA 证书
Cookie 浏览器自动携带 需手动同步
架构角色 信使（纯转发） 代理（中间人）

8.2 桥接服务器架构

bridge_server.py
├── WebSocket 服务器 (ws://127.0.0.1:9999/ws)
│   ├── 接收浏览器连接（只保持一个活跃连接）
│   ├── 心跳保持 (每 15s ping/pong)
│   └── 转发 JSON 请求 / 接收 JSON 响应
│
├── HTTP 服务器 (http://127.0.0.1:9998)
│   ├── POST /proxy  ← Yakit 发包入口（JSON 格式）
│   ├── GET  /status ← 桥接状态查询
│   └── GET  /       ← 服务信息
│
└── 线程安全通信
    ├── threading.Event  (跨线程唤醒)
    ├── threading.Lock   (保护 pending_requests 字典)
    └── asyncio.run_coroutine_threadsafe  (HTTP → WS 消息投递)

通信协议（全 JSON）：

Yakit → bridge_server:
POST /proxy HTTP/1.1
Host: 127.0.0.1:9998
Content-Type: application/json

{"method":"POST","url":"/api/web/login","headers":{...},"body":"{...}"}

bridge_server → 浏览器 (WebSocket):
{"type":"request","id":1,"method":"POST","url":"/api/web/login","headers":{...},"body":"{...}"}

浏览器 → bridge_server (WebSocket):
{"type":"response","id":1,"status":200,"statusText":"OK","headers":"...","body":"..."}

bridge_server → Yakit (HTTP Response):
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
X-Bridge: proxied

{"success":false,"message":"账号或密码错误",...}

准确来说：桥接服务器不生成任何加密或签名，也不做 URL 转换。它只是一个双向 JSON 信使 —— 接收 Yakit 的 JSON 请求 → 通过 WebSocket 发给浏览器 → 浏览器 sendRawRequest() 用原生 XHR 发送 → 某动态防护产品 JS 自动对修改后的请求重新加密+签名 → 响应原路返回。

8.5 桥接数据流完整跟踪

[1] 浏览器捕获请求 #0, POST /api/web/login
    Body: {"account":"138****8000","password":"xxx","captcha":"abcd"}

[2] __VV.toYakit(0) → 自动剥离签名参数 → 包装为桥接 JSON → 复制到剪贴板

[3] 粘贴到 Yakit → 修改 body → 发送

[4] bridge_server.py 收到 POST /proxy:
    → 解析 JSON → ws_send_request_sync() → WebSocket 发送到浏览器

[5] 浏览器 __VV._bridgeWs.onmessage 接收:
    → type: 'request' → 调用 sendRawRequest(url, {method, headers, body})
    → 原生 XHR 发送到目标站（cookie 自动携带，某动态防护产品 JS 自动重新签名）

[6] 目标站返回响应 → sendRawRequest resolve → WebSocket 回传 bridge_server.py

[7] bridge_server.py → HTTP Response → Yakit 显示

9. Burp Suite 集成方案

9.1 方案概述

Burp Suite 作为 MITM 代理抓包时，流量已经经过某动态防护产品加密（body 乱码、URL 有签名参数），无法直接修改。桥接架构同样兼容 Burp Suite —— 在 Burp 中将修改后的请求转为 JSON 发送到 bridge_server。

9.2 配置方法

方法 A：Burp Repeater 手动发送

在 Burp Repeater 中构造以下请求：

POST /proxy HTTP/1.1
Host: 127.0.0.1:9998
Content-Type: application/json
Content-Length: 256

{"method":"POST","url":"/api/web/login","headers":{"Content-Type":"application/json;charset=utf-8","Accept":"application/json"},"body":"{\"account\":"demo_user",\"password\":"[REDACTED]"}"}

方法 B：Burp 插件自动化（可选扩展）

可以编写 Burp 扩展实现： 1. 拦截 Burp Proxy 中经过某动态防护产品加密的请求 2. 从油猴脚本获取该请求对应的原始 body（通过 HTTP 接口） 3. 在 Burp 中修改原始 body 4. 自动转发到 bridge_server

此方案为高级扩展，具体实现取决于实际需求。

9.3 Burp vs Yakit 对比

对比维度 Yakit WebFuzzer Burp Repeater
上手难度 ★☆☆（粘贴即用） ★★☆（需手动构造 Host）
参数编辑 JSON 内修改 同上
批量重放 WebFuzzer 原生支持 Intruder 支持
响应对比 内置 Diff 工具 Comparer 工具
中文支持 ✅ 原生支持 ⚠️ 部分乱码

11. 跨站点适配

11.1 通用性分析

本工具核心机制（原型链逃逸 + 实例级 Hook + .call() 绕过）是某动态防护产品 WAF 的通用绕过手段，适用于所有使用某动态防护产品动态防护的站点。

组件 通用性 说明
实例级 Hook（截获原始参数） ✅ 通用 依赖 JS 原型链机制，与某动态防护产品版本/站点无关
sendRawRequest 绕过引擎 ✅ 通用 原生 XHR 引用 + .call()，不经过任何 Hook
WebSocket 桥接架构 ✅ 通用 纯通信层，完全不依赖目标站点
_stripRSQuery 签名剥离 ✅ 通用 双方案自动检测，自适应参数名特征
反调试拦截 ✅ 通用 只拦截通用 debugger 模式，不碰 VM
toYakit 导出 ✅ 通用 自动适配任意路径/参数
签名参数检测参数 ⚠️ 按需调整 _rsKeyMinLen、_rsValMinLen、_rsKeyPattern
静态资源过滤 _isAPI ⚠️ 按需调整 不同站点的静态资源目录不同

某动态防护产品特征 兼容性 说明
$_ts.nsd 配置项 ✅ 不影响绕过，只是配置标识

11.6 强制签名校验站点处理

如果新站点的某动态防护产品是强制校验签名（即不带签名的请求一定返回 412）：

方案 可行性 说明
浏览器内 sendRawRequest ✅ 可用 跑在已验证会话里，WAF 信任浏览器的 TLS/HTTP 指纹
toYakit() 直发 ❌ 412 外部 HTTP 客户端，无浏览器环境
桥接模式 ✅ 可用 通过浏览器转发，继承已验证会话，某动态防护产品 JS 自动重签名
调用某动态防护产品 VM 签名函数 ❌ 不可行 VM 混淆极深，逆向成本极高

结论：遇到强制校验站点时，桥接模式是唯一的外部发包方案。浏览器内操作（sendRawRequest、replay）不受影响。

前端加密适配流程
═══════════════════════════════════════════

□ 1. 用 catalog() / inspect() 确认 body 中有加密字段
□ 2. 搜索加密函数（按第 4.3 节四步法）

12. 故障排查

现象 原因 解决
控制台无 [VV] 🚀 v2.0 已注入 脚本未启用或 @match 不匹配 检查 Tampermonkey 面板
Body 显示乱码而非 JSON 实例级 Hook 未生效 确认 @run-at document-start + @inject-into page
页面卡在 debugger 循环 Chrome/Edge 未禁用断点 刷新后按 Ctrl+F8
sendRawRequest 返回 404 URL 路径缺少 API 前缀 检查 __VV.catalog() 显示的完整路径
sendRawRequest 返回 scf:"-1" 正常现象 所有请求都有此字段，不是 WAF 拦截
面板按钮点击无反应 脚本版本过旧 升级到 v2.0（inline onclick 版）
Yakit 直发返回 412 从外部 HTTP 客户端发请求 使用桥接模式
桥接 no_browser 浏览器未连接桥接 点击 🌉 桥接启动 或 __VV.startBridge()
桥接返回 400 URL 中有某动态防护产品签名参数 确认 toYakit 导出时 clean: true
桥接超时 bridge_server.py 未启动或端口被占 检查终端是否运行、netstat -an \| findstr 9999
Yakit TLS连接失败 协议选了 HTTPS 改为 HTTP（桥接不使用 TLS）
Yakit 404 not_found POST 路径不是 /proxy 确认第一行为 POST /proxy HTTP/1.1
Yakit empty_body Content-Length 为 0 或请求未带 body 确认粘贴了完整 JSON body

剪贴板复制失败 浏览器安全策略限制 手动选中控制台输出的 JSON 文本 Ctrl+C
WebSocket 连接失败 防火墙阻止 确认 9999 端口未被防火墙拦截
